<a id="crdb-export-parquet-decimal"></a>
### CockroachDB EXPORT INTO PARQUET corrupts DECIMAL

- **Versions:** CockroachDB v25.4.13
- **Seen:** 21.00 read back as 2155734753.76, in Databricks and DuckDB alike
- **Cause:** A DECIMAL column is written as BYTE_ARRAY annotated DECIMAL but filled with the number's text
- **Effect:** Snapshot rows with decimals are wrong
- **Fix or workaround:** Export decimals as text and cast back
- **Found:** 2026-10-20, zerobus-debezium-test SOURCE=crdb snapshot

<a id="db2-asncap-start-order"></a>
### Db2 ASN capture needs a set start order

- **Seen:** VALUES ASNCDC.ASNCDCSERVICES('start', ...) through ibm-db never returned; later, captured tables had no change rows
- **Cause:** The UDF starts the agent and stays attached to it when called from a driver; registrations are read when the agent starts
- **Effect:** Debezium sees no changes from tables that look registered
- **Fix or workaround:** Start asncap as the instance user (detached), register tables with ADDTABLE, then asnccmd reinit
- **Where:** skills/zerobus-debezium-test/scripts/debezium-zerobus.sh
- **Found:** 2026-10-24, zerobus-debezium-test SOURCE=db2 MODEL=tpch

<a id="db2-boolean-not-captured"></a>
### A Db2 BOOLEAN column stops ASN capture for every table

- **Versions:** Db2 11.5.9; Debezium 3.7.0.Final
- **Seen:** No change events for any TPC-DI table after T. ASNCDC.IBMSNAP_CAPTRACE: ASN0552E (SQLCODE -804) inserting into the change table of DIMDATE, then ASN0008I: the Capture program was stopped. Every registration still shows state A, and Debezium logs Starting streaming with no error
- **Cause:** Db2's SQL Replication (ASN capture), which Debezium's Db2 connector reads, doesn't support BOOLEAN; Debezium can only snapshot such tables (its documentation's data type table)
- **Effect:** Silent and database-wide: one table with a BOOLEAN column stops change capture for all tables
- **Fix or workaround:** Use SMALLINT 0/1 or CHAR(1) instead of BOOLEAN; check a schema for BOOLEAN columns before ADDTABLE; watch ASNCDC.IBMSNAP_CAPTRACE for ASN0008I and ASN0552E (capture stopped), since Debezium reports nothing. The test maps booleans to SMALLINT 0/1 on Db2
- **Where:** skills/zerobus-debezium-test/scripts/debezium-zerobus.sh
- **References:** https://debezium.io/documentation/reference/stable/connectors/db2.html#db2-data-types
- **Found:** 2026-10-25, zerobus-debezium-test SOURCE=db2 MODEL=tpcdi

<a id="db2-json-object-decimal"></a>
### Db2's JSON_OBJECT writes decimals with leading zeros

- **Seen:** -999.99 came out as -0000000000999.99, which no JSON parser accepts
- **Cause:** JSON_OBJECT formats DECIMAL with the column's full precision
- **Effect:** JSON built in Db2 (triggers, exports) with decimals is invalid
- **Fix or workaround:** Cast decimals to VARCHAR before JSON_OBJECT
- **Where:** skills/zerobus-debezium-test/scripts/sources/audit-triggers.py
- **Found:** 2026-10-24, zerobus-debezium-test SOURCE=db2 MODEL=tpch

<a id="db2-json-object-timestamp-format"></a>
### Db2's JSON_OBJECT writes timestamps in its own text form

- **Seen:** History check: expected 1970-01-01-00.00.01.000000, silver had 1970-01-01 00:00:01.000000
- **Cause:** JSON_OBJECT renders a TIMESTAMP in Db2's character form (a dash between date and time, dots in the time), and a TIME as 00.00.01
- **Effect:** JSON built in Db2 (triggers, exports) has timestamps no ISO parser reads as such
- **Fix or workaround:** VARCHAR_FORMAT(x, 'YYYY-MM-DD HH24:MI:SS.FF6') for timestamps (and times on a fixed date) before JSON_OBJECT
- **Where:** skills/zerobus-debezium-test/scripts/sources/audit-triggers.py
- **Found:** 2026-10-24, zerobus-debezium-test SOURCE=db2 MODEL=tpcc

<a id="informix-case-lvarchar-padding"></a>
### Informix pads a CASE with an LVARCHAR cast to 2048

- **Seen:** Audit JSON for date_dim was cut off at its 32000-character column; each integer was followed by blanks
- **Cause:** CASE WHEN x IS NULL THEN 'null' ELSE x::LVARCHAR END returns a fixed-width result, blank-padded to LVARCHAR's 2048
- **Effect:** Text built in Informix SQL (triggers, exports) grows past column limits and is truncated
- **Fix or workaround:** TRIM each such CASE
- **Where:** skills/zerobus-debezium-test/scripts/sources/audit-triggers.py
- **Found:** 2026-10-24, zerobus-debezium-test SOURCE=informix MODEL=tpcds

<a id="informix-lock-wait"></a>
### Informix fails concurrent writers at once instead of waiting

- **Seen:** Error -425 / ISAM -107 (record locked) while filling with several sessions
- **Cause:** The default lock mode is NOT WAIT
- **Effect:** Parallel loaders or applications get errors under contention
- **Fix or workaround:** SET LOCK MODE TO WAIT <seconds> per session
- **Where:** skills/lfc-source-datagen/scripts/python/drivers.py
- **Found:** 2026-10-24, zerobus-debezium-test SOURCE=informix MODEL=tpcds, tpce

- **Seen:** An UPDATE setting a row to its own values: the audit trigger fired, but no CDC row and no Debezium event

<a id="mysql-fk-actions-not-in-binlog"></a>
### MySQL and MariaDB don't log foreign key actions

- **Versions:** MySQL through 9.5, MariaDB; MySQL 9.6 and later log them (SQL-layer foreign keys)
- **Seen:** A parent row deleted in the application; its children are gone at the source but still in silver
- **Cause:** InnoDB carries out ON DELETE CASCADE and SET NULL inside the storage engine and writes no binlog event for the child rows (documented in the MySQL manual)
- **Effect:** Any binlog reader misses the child deletes and updates: the target keeps rows the source no longer has
- **Fix or workaround:** Apply the actions in silver after each update from the foreign keys (the source enforces them, so an orphan is a missed cascade), and record each in a trace table
- **Not affected:** postgres, sqlserver, oracle, mysql 9.6+
- **Where:** skills/zerobus-debezium-test/scripts/fk-actions.py, skills/zerobus-debezium-test/scripts/fk-cascade-check.sh, skills/cdc-table-plan/scripts/classify.py
- **References:** https://dev.mysql.com/doc/refman/8.4/en/innodb-and-mysql-replication.html
- **Notes:** Lakeflow Connect's MySQL connector reads the binlog too: not tested here for this case. ON UPDATE CASCADE and SET DEFAULT aren't handled
- **Found:** 2026-10-24, zerobus-debezium-test SOURCE=mysql APP=mautic; fk-cascade-check.sh on MySQL 8.4, 9.6, MariaDB, PostgreSQL 16, SQL Server 2022, Oracle 23ai

### A MySQL trigger naming a dropped column fails writes

- **Seen:** After ALTER TABLE ... DROP COLUMN, every INSERT and UPDATE on the table failed
- **Cause:** MySQL keeps the trigger body as text and resolves NEW.<column> at run time; the drop doesn't touch or check triggers
- **Effect:** An audit or sync trigger on the source blocks the application's writes after a schema change
- **Fix or workaround:** Recreate the table's triggers from the schema after a schema change (audit-triggers.py --only T --replace)
- **Where:** skills/zerobus-debezium-test/scripts/sources/audit-triggers.py
- **Found:** 2026-10-24, zerobus-debezium-test SOURCE=mysql MODEL=tpch rounds 4-5

<a id="pg16-lowering-wal-level-stops-start"></a>
### PostgreSQL 16: lowering wal_level with logical slots present stops the server

- **Versions:** PostgreSQL 16.15
- **Seen:** FATAL: logical replication slot "<slot>" exists, but wal_level < logical. The container exits on restart.
- **Cause:** PostgreSQL's startup check. PostgreSQL 16 doesn't invalidate the slots.
- **Effect:** The server doesn't start until the slots are dropped or wal_level is raised again.
- **Fix or workaround:** Drop the logical slots first, then lower wal_level. On PostgreSQL 16 check a lost slot with wal_status; invalidation_reason exists from PostgreSQL 17.
- **Where:** skills/lfc-source-setup/references/engine-postgres.md
- **Found:** 2026-10-25, expected-entry test round 2026-10-25: PostgreSQL 16.15

### SQL Server: governor limits on the gateway's login end a snapshot early or refuse it
